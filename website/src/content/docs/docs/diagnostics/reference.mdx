## Conversion

Why a statement was not converted.

### SQ0001

**the SQL does not parse** (`parse_fidelity`)

SQLQuack's Snowflake parser could not read the SQL, so nothing in it was converted. The span points where the parser stopped and the label carries the parser's message. Check the SQL at that point against Snowflake's grammar; if Snowflake accepts the statement, SQLQuack's parser is missing the syntax and the statement should be reported with the label. Where the line holds dbt Jinja, the help says to compile the model with dbt first, since Snowflake does not parse Jinja either.

**Example:**

```sh
echo "SELECT a, FROM orders WHERE (b = 1" | sqlquack check
```

### SQ0002

**SQLQuack can't convert this yet** (`missing_rule`)

SQLQuack converts only what it has checked against results recorded in Snowflake. Nothing checked converts the construct at the span yet, so the statement is refused rather than turned into SQL that might mean something else in DuckDB. Rewrite the statement without it; `sqlquack census` shows which constructs a body of SQL needs.

**Example:**

```sh
echo "SELECT WEEKISO(CURRENT_DATE()) AS w" | sqlquack convert --no-config
```

### SQ0003

**SQLQuack can't convert this for these types** (`type_condition`)

SQLQuack converts the construct at the span only for the types checked against Snowflake, and the values here have other types, or types SQLQuack could not work out. Declaring the relation's columns and types in the project's sources often settles the types; an explicit cast to a supported type also works when it keeps the statement's meaning.

**Help:** declare the columns' Snowflake types in the project's sources, or cast the values to a type it supports; for a function, cast them to a type the label names

**Example:**

```sh
echo "SELECT FLOOR('abc') AS f" | sqlquack convert --no-config
```

### SQ0004

**SQLQuack doesn't know this name** (`unresolved_name`)

Converting a statement needs to know what each relation and column name refers to and what type it has. The name at the span is unknown, or matches more than one column. Add the relation and its columns to a source file in the project's `sources/` folder, or qualify an ambiguous column with its relation.

**Help:** declare the relation and its columns in a source file of the project (`sources/*.yml`)

**Example:**

```sh
echo "SELECT a FROM orders" | sqlquack convert --no-config
```

### SQ0005

**DuckDB can't do what Snowflake does here** (`not_expressible`)

The construct at the span does something in Snowflake that DuckDB has no way to reproduce, for the reason in the label, so no later version will convert it as written. Rewrite the statement so it does not depend on that behaviour.

**Example:** no construct is declared inexpressible yet; one would be refused with the reason as its label

### SQ0006

**Converting this took too long or produced too much SQL** (`conversion_budget`)

Converting the statement took longer, or produced more DuckDB SQL, than SQLQuack allows for one statement, which keeps one unusual input from stalling a run. Splitting the statement, for example into common table expressions or separate statements, usually brings it under the limit.

**Help:** split the statement into smaller statements

**Example:** a statement whose conversion runs past the time budget or emits more DuckDB SQL than it allows

### SQ0007

**SQLQuack can't convert for these session settings** (`session_parameters`)

Converted SQL is checked against Snowflake under particular session settings. The settings given differ from every checked set, so nothing is known to convert correctly for that session. The label names the settings; settings left unset take Snowflake's documented defaults.

**Help:** run the SQL in a session whose settings SQLQuack has checked

**Example:**

```sh
echo "SELECT 1 AS one" | sqlquack convert --no-config --session WEEK_START=1
```

### SQ0008

**This needs a known difference that isn't allowed** (`divergence_refused`)

The construct at the span converts only with a known difference between Snowflake and DuckDB, where DuckDB may raise an error or give a different value. The message names it, the label says what differs, and the note says when that is fine and when it is wrong. sqlquack.toml, or the defaults without one, does not allow it here, so the statement is refused. Allow it if your use is one where it is fine, or rewrite the statement without the construct; `sqlquack explain --differences` lists every known difference and whether it is allowed.

**Help:** the help gives the one fix that works here, such as allowing the known difference in sqlquack.toml; `sqlquack explain &lt;name>` describes it

**Example:**

```sh
echo "SELECT HASH(1) AS h" | sqlquack convert --no-config
```

### SQ0009

**This column needs an alias, because SQLQuack can't be sure of the name Snowflake gives it** (`unaliased_output_name`)

Snowflake names an unaliased select item after its written text, upper-cased in full with spacing, comments and quotes kept and cut at 255 characters, and a converted query must return the same column names. SQLQuack writes that name as an alias for the shapes checked against Snowflake: literals in any spelling, columns, arithmetic, ||, comparisons, AND, OR, NOT, IS NULL, parentheses, casts, CASE, IFF, the clock functions and a list of functions and aggregates, nested freely. Other items, such as paths, window functions, non-ASCII text, line comments or unlisted functions, are refused rather than converted under a name that might differ. The help suggests the exact alias; an alias fixes the name in both engines.

**Help:** add an alias, such as `AS total`, which names the column in both engines

**Example:**

```sh
echo "SELECT 'café' || 'b'" | sqlquack convert --no-config
```

## Input limits

Limits that keep parsing and conversion bounded.

### SQ0101

**the input is larger than the parser accepts** (`input_too_large`)

The parser refuses inputs beyond a fixed size so that one input cannot exhaust memory. Split the SQL into several inputs and convert each.

**Help:** split the input into smaller files

**Example:**

```sh
python3 -c "print('SELECT 1;' * 2000000)" | sqlquack check
```

Also reported by its guard name, `E_GUARD_INPUT_TOO_LARGE`.

### SQ0102

**the input has more tokens than the parser accepts** (`token_budget_exceeded`)

The parser refuses inputs with more tokens than its budget so that parsing time stays bounded. Split the SQL into several statements or inputs.

**Help:** split the input into smaller statements or files

**Example:**

```sh
python3 -c "print('SELECT 1;' * 400000)" | sqlquack check
```

Also reported by its guard name, `E_GUARD_TOKEN_BUDGET_EXCEEDED`.

### SQ0103

**brackets nest deeper than the parser accepts** (`nesting_depth_exceeded`)

Parentheses, brackets and braces nest deeper at the span than the parser's limit. The limit keeps parsing from exhausting the stack. Redundant parentheses can be removed; deeply nested subqueries can usually become common table expressions.

**Help:** remove redundant parentheses, or move nested parts into common table expressions

**Example:**

```sh
python3 -c "print('SELECT ' + '(' * 600 + '1' + ')' * 600)" | sqlquack check
```

Also reported by its guard name, `E_GUARD_NESTING_DEPTH_EXCEEDED`.

### SQ0104

**the statement nests deeper than the parser accepts** (`parser_depth_exceeded`)

The parser's recursion reached its depth limit at the span. The limit keeps parsing from exhausting the stack. Restructure the deepest part of the statement, for example with common table expressions.

**Help:** move nested parts into common table expressions

**Example:**

```sh
python3 -c "print('SELECT ' + 'NOT ' * 2000 + 'TRUE')" | sqlquack check
```

Also reported by its guard name, `E_GUARD_PARSER_DEPTH_EXCEEDED`.

### SQ0105

**the parsed statement nests deeper than SQLQuack accepts** (`ast_depth_exceeded`)

The statement parsed, but its tree nests deeper than the limit SQLQuack places on later analysis, which keeps conversion from exhausting the stack. Restructure the deepest part of the statement.

**Help:** move nested parts into common table expressions

**Example:**

```sh
python3 -c "print('SELECT ' + 'CASE WHEN TRUE THEN ' * 600 + '1' + ' END' * 600)" | sqlquack check
```

Also reported by its guard name, `E_GUARD_AST_DEPTH_EXCEEDED`.

### SQ0106

**the parsed statement is larger than SQLQuack accepts** (`ast_budget_exceeded`)

The statement parsed into more tree nodes than SQLQuack's budget, which keeps conversion time and memory bounded. Split it into smaller statements.

**Help:** split the statement into smaller statements

**Example:** a statement that parses into more than a million tree nodes

Also reported by its guard name, `E_GUARD_AST_BUDGET_EXCEEDED`.

### SQ0107

**function calls nest deeper than SQLQuack accepts** (`function_nesting_depth_exceeded`)

Function calls nest inside each other deeper than SQLQuack's limit at the span. Compute the innermost calls in a common table expression or a subquery and refer to their results.

**Help:** compute inner calls in a common table expression first

**Example:**

```sh
python3 -c "print('SELECT ' + 'ABS(' * 300 + '1' + ')' * 300)" | sqlquack check
```

Also reported by its guard name, `E_GUARD_FUNCTION_NESTING_DEPTH_EXCEEDED`.

## SQL Snowflake rejects

SQL that parses but that Snowflake rejects when it runs.

### SQ0201

**Snowflake does not support INTERSECT, EXCEPT or MINUS with ALL** (`set_operation_all`)

Snowflake accepts ALL only after UNION. INTERSECT ALL, EXCEPT ALL and MINUS ALL parse, but Snowflake rejects them as an unsupported feature, so there is no Snowflake meaning to convert. Without ALL the operators compare distinct rows; keeping duplicates needs a rewrite, for example numbering each row with ROW_NUMBER() over all columns and comparing those pairs.

**Help:** drop ALL to compare distinct rows; only UNION accepts ALL in Snowflake

**Example:**

```sh
echo "SELECT id FROM orders INTERSECT ALL SELECT id FROM returns" | sqlquack check
```

### SQ0202

**Snowflake does not support WAIT in FOR UPDATE** (`lock_wait`)

FOR UPDATE WAIT n parses, but Snowflake rejects it as an unsupported feature, so the statement never runs there. Remove the WAIT clause; Snowflake's lock timeout comes from the LOCK_TIMEOUT session parameter instead.

**Help:** remove the WAIT clause

**Example:**

```sh
echo "SELECT order_id FROM orders FOR UPDATE WAIT 7" | sqlquack check
```

### SQ0203

**QUALIFY needs a window function** (`qualify_without_window`)

Snowflake evaluates QUALIFY after window functions, and rejects a QUALIFY clause when neither the SELECT list nor QUALIFY itself calls a window function (Snowflake error 992). A window function the QUALIFY condition reaches through a SELECT-list alias counts. A condition on plain columns belongs in WHERE, and one on aggregates in HAVING.

**Help:** move the condition to WHERE or HAVING, or filter on a window function's result

**Example:**

```sh
echo "SELECT 1 QUALIFY TRUE" | sqlquack check
```

### SQ0204

**REPLACE or RENAME names a column the star's ILIKE pattern removed** (`star_filter_drops_named_column`)

In `* ILIKE 'pattern' REPLACE (...)` or `RENAME (...)`, Snowflake applies the pattern first, ignoring case, and rejects a REPLACE or RENAME of a column the pattern did not keep (Snowflake error 1431). A name that fails the pattern ignoring case fails it whatever the table holds, so no schema is needed to see it.

**Help:** name a column the ILIKE pattern keeps, or widen the pattern

**Example:**

```sh
echo "SELECT * ILIKE '%_id' REPLACE (price * 2 AS price) FROM orders" | sqlquack check
```

### SQ0205

**A window function needs an OVER clause** (`window_without_over`)

CUME_DIST, PERCENT_RANK and NTH_VALUE are window functions only: Snowflake rejects a call to one without an OVER clause when compiling the query (Snowflake error 2064, missing window specification), so the statement never runs there. Add the OVER clause that says which rows the function ranks or reads.

**Help:** add an OVER clause, such as `OVER (ORDER BY ...)`

**Example:**

```sh
echo "SELECT CUME_DIST() AS d FROM orders" | sqlquack check
```

### SQ0206

**Unknown function ==** (`double_equals`)

Snowflake has no `==` operator. The statement parses, but Snowflake reads `==` as a call to a function of that name and rejects the query when compiling it (Snowflake error 2139, unknown function), so the statement never runs there. Other dialects read `==` as `=`; SQLQuack does not, because that would convert SQL Snowflake rejects. Write `=` instead.

**Help:** compare with `=`

**Example:**

```sh
echo "SELECT order_id FROM orders WHERE status == 'shipped'" | sqlquack check
```

### SQ0211

**Snowflake has no literal of this date-time type** (`unsupported_type_literal`)

Only DATE, TIME and TIMESTAMP take a string as a typed literal in Snowflake, and only without a precision. A date-time type with a precision before a string, such as TIMESTAMP_NTZ(3), DATETIME(3), TIMESTAMP(3) or TIME(3), parses, but Snowflake rejects it as an unsupported data type literal (Snowflake error 2121). Without a precision, TIMESTAMP_NTZ, TIMESTAMP_LTZ, TIMESTAMP_TZ or DATETIME before a string is a syntax error. Cast the string with `::` or CAST, or call TO_TIMESTAMP_NTZ, TO_TIMESTAMP_LTZ, TO_TIMESTAMP_TZ, TO_TIMESTAMP or TO_TIME.

**Help:** cast the string instead, e.g. `'2026-01-02'::TIMESTAMP_NTZ(3)`

**Example:**

```sh
echo "SELECT TIMESTAMP_NTZ(3) '2026-01-02 03:04:05' AS v" | sqlquack check
```
