Where SQL translation goes wrong

Snowflake rejects it at runtime

Invalid Snowflake SQL only shows up when the query runs on the warehouse, often mid-pipeline.

Tests pass for the wrong engine

On DuckDB, NULLs, decimals and casts behave differently, with no error. Your tests go green locally and the numbers differ in production.

Support depends on the types

A function can convert for one precision and overflow on another. "Supported" means nothing without the types involved.

Best effort means guessing

Most transpilers rewrite what they don't understand and hope. There's no way to tell which parts are guesses.

From Snowflake SQL to DuckDB SQL

Check it, convert it, and know exactly what was refused and why.

01 · Check

Catch what Snowflake would reject

Parses Snowflake SQL and reports the syntax Snowflake would reject. No schema needed. Each error has a code and the exact span; rejections also come with a fix.

How checking works →

sqlquack check
error[SQ0201]: Snowflake does not support INTERSECT, EXCEPT or MINUS with ALL
 --> <stdin>:1:29
  |
1 | SELECT order_id FROM orders INTERSECT ALL SELECT order_id FROM orders
  |                             ^^^^^^^^^^^^^ Snowflake does not support INTERSECT with ALL
  |
  = help: drop ALL to compare distinct rows; only UNION accepts ALL in Snowflake
02 · Convert

DuckDB SQL that keeps Snowflake's meaning

Uses your sources' types and only verified rules. NUMBER(12,2) / 3 keeps Snowflake's 8 decimal places.

How conversion works →

-- div.sql, with TOTAL as NUMBER(12,2) in sources/orders.yml
SELECT order_id, total / 3 AS third FROM orders

sqlquack convert div.sql --builtin-policy
SELECT
    "ORDERS"."ORDER_ID" AS "ORDER_ID",
    (CASE
        …
        ELSE CAST(… AS DECIMAL(18,8))
    END) AS "THIRD"
FROM "ORDERS" AS "ORDERS"
sqlquack convert: done, converted under the built-in default
03 · Refuse precisely

A refusal you can act on

No verified rule, no conversion. The refusal underlines the construct and says what to change.

Every diagnostic code →

sqlquack convert due.sql --builtin-policy
error[SQ0008]: the conversion needs a known divergence the policy refuses: `fn:HASH`
 --> due.sql:2:8
  |
2 |        HASH(customer_id) AS bucket
  |        ^^^^^^^^^^^^^^^^^ fn:HASH needs known divergence `hash`,
  |          which the policy refuses in this mode
  |
  = help: the built-in policy refuses every known divergence;
          pass --policy with a policy file that allows `hash` …
sqlquack convert: refused, 1 refusal under the built-in default
04 · Decide what to accept

Known divergences are opt-in

Some conversions differ in one documented way, like HASH. The policy file lists each one and whether it's allowed; the built-in default refuses them all.

Configure the policy →

# sqlquack.toml (excerpt)
[divergences.hash]
default = "warn"

sqlquack convert due.sql
SELECT
    "ORDERS"."ORDER_ID" AS "ORDER_ID",
    … AS "BUCKET"
FROM "ORDERS" AS "ORDERS"
sqlquack convert: relies on known divergence hash at fn:HASH
sqlquack convert: done, converted under utc-v1

06 · Use it from Python

The same engine, as a library

The same engine as the CLI, with typed results and diagnostics.

Python API →

import sqlquack

result = sqlquack.check(sql="SELECT 1 QUALIFY TRUE")
result.diagnostics[0].code   # "SQ0203"

conversion = sqlquack.convert(
    sql="SELECT 1 AS total",
    options=sqlquack.ConvertOptions(builtin_policy=True),
)
conversion.converted          # True
