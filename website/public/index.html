Same answer, or a clear no

A SQLGlot alternative in Rust that would rather reject your SQL than return the wrong answer.

SQLQuack checks Snowflake SQL with Rust-style diagnostics and converts it to DuckDB only where rules checked against recorded Snowflake results cover the types involved. Everything else is refused with the exact span and the reason, or stopped by a declared guard where DuckDB's result would differ.

Where SQL translation goes wrong

It transpiles, runs, and differs

NULL handling, decimal arithmetic and implicit casts behave differently on DuckDB, with no error.

Tests pass for the wrong engine

Local tests pass for behaviour your warehouse doesn't have.

"Supported" isn't one fact

A function can convert for one precision and overflow on another. Support depends on the types involved.

Two kinds of error, mixed up

SQL that is invalid on Snowflake and valid SQL that can't be translated safely need different fixes.

From Snowflake SQL to DuckDB SQL

Check it, convert it, and know exactly what was refused and why.

01 · Check

Catch what Snowflake would reject

sqlquack check parses Snowflake SQL and reports what Snowflake rejects, without a schema or a conversion. Each problem has an SQ code, the exact span and a fix.

How checking works →

sqlquack check
error[SQ0201]: Snowflake does not support INTERSECT, EXCEPT or MINUS with ALL
 --> <stdin>:1:29
  |
1 | SELECT order_id FROM orders INTERSECT ALL SELECT order_id FROM orders
  |                             ^^^^^^^^^^^^^ Snowflake does not support INTERSECT with ALL
  |
  = help: drop ALL to compare distinct rows; only UNION accepts ALL in Snowflake
02 · Convert

DuckDB SQL that keeps Snowflake's meaning

sqlquack convert types every expression from your schema and applies only verified rules. Here a NUMBER(12,2) divided by 3 keeps Snowflake's scale of 8, and division by zero still raises. DuckDB parses and binds every converted statement before it is printed.

How conversion works →

sqlquack convert div.sql --schema schema.json
SELECT "ORDERS"."ORDER_ID" AS "ORDER_ID",
  (CASE WHEN "ORDERS"."TOTAL" IS NULL OR … THEN NULL
        WHEN CAST(3 AS DECIMAL(1,0)) = 0
        THEN CAST(CAST('sqlquack:100051#e539322555ff: Division by zero' AS INTEGER) AS "NULL")
        ELSE CAST(… AS DECIMAL(18,8)) END) AS "THIRD",
  (CASE WHEN ("ORDERS"."STATUS" = 'shipped')
        THEN CAST(CAST(1 AS DECIMAL(1,0)) AS DECIMAL(1,0))
        ELSE CAST(CAST(0 AS DECIMAL(1,0)) AS DECIMAL(1,0)) END) AS "SHIPPED"
FROM "ORDERS" AS "ORDERS"
sqlquack convert: done, converted under the built-in default
03 · Refuse precisely

A refusal you can act on

When no verified rule covers a construct, or DuckDB would only approximate it, SQLQuack refuses the statement instead of guessing. The refusal names the construct, underlines it and says what to change.

Every diagnostic code →

sqlquack convert due.sql --schema schema.json
error[SQ0008]: the conversion needs a known divergence the policy refuses: `fn:HASH`
 --> due.sql:2:8
  |
2 |        HASH(customer_id) AS bucket
  |        ^^^^^^^^^^^^^^^^^ fn:HASH needs known divergence `hash`,
  |          which the policy refuses in this mode
  |
  = help: allow the divergence under [divergences.<id>] in the policy file …
sqlquack convert: refused, 1 refusal under the built-in default
04 · Decide what to accept

Known divergences are opt-in

Some conversions are exact except for a documented difference, such as HASH, which DuckDB computes with its own function. The policy file lists each one, and nothing that relies on one converts until you allow it.

Configure the policy →

# sqlquack.toml (excerpt)
[divergences.hash]
default = "warn"

sqlquack convert due.sql --schema schema.json
SELECT "ORDERS"."ORDER_ID" AS "ORDER_ID", … AS "BUCKET" FROM "ORDERS" AS "ORDERS"
sqlquack convert: relies on known divergence hash at fn:HASH
sqlquack convert: done, converted under utc-v1

06 · Use it from Python

The same engine, as a library

The sqlquack Python package runs the same code as the command line and returns frozen results with typed diagnostics.

Python API →

import sqlquack

result = sqlquack.check(sql="SELECT 1 QUALIFY TRUE")
result.diagnostics[0].code   # "SQ0203"

conversion = sqlquack.convert(
    sql="SELECT 1 AS total",
    options=sqlquack.ConvertOptions(builtin_policy=True),
)
conversion.converted          # True

Start in a minute

Build it from source, then check a file or convert it with a schema of your relations.

  • Snowflake to DuckDB, for running warehouse SQL against small fixtures locally or in CI.
  • No account, server or Snowflake connection needed. SQLBuild isn't required.
  • One binary for the command line, and a Python package with the same engine.
  • Free and open source, Apache-2.0.
git clone https://github.com/sqlstack-io/sqlquack && cd sqlquack
echo "SELECT 1 QUALIFY TRUE" | cargo run --release -p sqlquack -- check
error[SQ0203]: QUALIFY needs a window function
…
echo "SELECT 1 AS total" | cargo run --release -p sqlquack -- convert --builtin-policy
SELECT CAST(1 AS DECIMAL(1,0)) AS "TOTAL"
sqlquack convert: done, converted under the built-in default
