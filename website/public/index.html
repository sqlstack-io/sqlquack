Where SQL translation goes wrong

The warehouse rejects it at runtime

Invalid SQL only shows up when the query runs on the warehouse, often mid-pipeline.

Tests pass for the wrong engine

On DuckDB, NULLs, decimals and casts behave differently, with no error. Your tests go green locally and the numbers differ in production.

Support depends on the types

A function can convert for one precision and overflow on another. "Supported" means nothing without the types involved.

Best effort means guessing

Most transpilers rewrite what they don't understand and hope. There's no way to tell which parts are guesses.

01 · Check

Catch what the warehouse would reject

Snowflake today: parses Snowflake SQL and reports the syntax Snowflake would reject. No schema needed. Each error has a code and the exact span; rejections also come with a fix.

How checking works →

sqlquack check

 --> <stdin>:1:29
  |
1 | SELECT order_id FROM orders INTERSECT ALL SELECT order_id FROM orders
  |                             ^^^^^^^^^^^^^ Snowflake does not support INTERSECT with ALL
  |
  = help: drop ALL to compare distinct rows; only UNION accepts ALL in Snowflake
02 · Convert

DuckDB SQL that keeps Snowflake's meaning

Uses your sources' types and only verified rules. NUMBER(12,2) / 3 keeps Snowflake's 8 decimal places.

How conversion works →

-- div.sql, with TOTAL as NUMBER(12,2) in sources/orders.yml
SELECT order_id, total / 3 AS third FROM orders

sqlquack convert div.sql --no-config
SELECT
    "ORDERS"."ORDER_ID" AS "ORDER_ID",
    CAST(CAST((
        sign(CAST(CAST("ORDERS"."TOTAL" AS DECIMAL(38, 2)) * 100000000 AS HUGEINT))
        * (
            (
                2 * abs(CAST(CAST("ORDERS"."TOTAL" AS DECIMAL(38, 2)) * 100000000 AS HUGEINT)) + 3
            )
            // 6
        )
    ) AS DECIMAL(38, 0))
    * 0.00000001 AS DECIMAL(18, 8)) AS "THIRD"
FROM "ORDERS" AS "ORDERS"
sqlquack convert: done, converted
03 · Refuse precisely

A refusal you can act on

No verified rule, no conversion. The refusal underlines the construct and says what to change.

Every diagnostic code →

sqlquack convert due.sql --no-config
error[SQ0008]: HASH gives a different value in DuckDB
 --> due.sql:2:8
  |
2 |        HASH(customer_id) AS bucket
  |        ^^^^^^^^^^^^^^^^^ DuckDB computes its own hash,
  |          never Snowflake's
  |
  = note: Equal inputs still get equal hashes within one run.
  = note: fine when: Joins, grouping, removing duplicates and
          spotting changed rows by hash.
  = note: wrong when: Storing, comparing or sorting by the hash
          value itself: it differs, with no error.
  = help: allow it in a sqlquack.toml …;
          `sqlquack explain hash` says when it is safe
sqlquack convert: refused, 1 refusal
04 · Decide what to accept

Known differences are your call

Some Snowflake behaviour has no exact match in DuckDB, like HASH. Each known difference says when it's fine and when it gives a wrong result. You refuse it, allow it or replace it with your own SQL.

Refuse, allow or replace →

# sqlquack.toml
[allow]
hash = true

sqlquack convert due.sql
SELECT
    "ORDERS"."ORDER_ID" AS "ORDER_ID",
    … AS "BUCKET"
FROM "ORDERS" AS "ORDERS"
sqlquack convert: done, converted (1 known difference
  allowed: hash — sqlquack explain hash)

06 · Use it from Python

The same engine, as a library

The same engine as the CLI, with typed results and diagnostics.

Python API →

import sqlquack

result = sqlquack.check(sql="SELECT 1 QUALIFY TRUE")
result.diagnostics[0].code   # "SQ0203"

conversion = sqlquack.convert(
    sql="SELECT 1 AS total",
    options=sqlquack.ConvertOptions(no_config=True),
)
conversion.converted          # True
